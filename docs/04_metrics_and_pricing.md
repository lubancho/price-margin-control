# 04. Методика метрик, алгоритм цены, предупреждения, сценарии

> Это главный документ проекта: по нему пишутся функции расчёта и тесты. Если код расходится с документом — ошибка в коде либо документ нужно обновить вместе с тестом.

## 1. Общие соглашения

| Соглашение | Правило |
|---|---|
| Деньги в БД | `NUMERIC(12,2)` для цен и сумм; `NUMERIC(12,4)` для себестоимости единицы (себестоимость считается по техкарте и бывает дробной) |
| Деньги в Python | `decimal.Decimal`, контекст с точностью 28 знаков. `float` допускается **только** в слое отображения (графики) |
| Доли | Хранятся долей `0…1` (`NUMERIC(6,4)`), на экране — процентами с 1 знаком |
| Округление денежных итогов | `ROUND_HALF_UP` до копеек, только на последнем шаге |
| Отсутствие значения | `NULL` / `None` → на экране «н/д». **Никогда не заменяем на 0**, если 0 исказит смысл |
| Период | Включительно: `date_from ≤ дата продажи ≤ date_to`, дата по местному времени точки (Asia/Omsk) |
| Товарное предложение | Пара «точка × товар», у которой есть действующая цена на дату расчёта |
| Активное предложение | Точка активна **и** товар активен **и** есть действующая цена |

### Как учитываются операции продажи

Каждая строка продажи имеет тип `sale` или `return` и флаг `is_cancelled`.

```
знак = 0,  если is_cancelled
знак = +1, если sale
знак = −1, если return

чистое_количество   = знак × quantity
чистая_выручка      = знак × (quantity × unit_price − discount_amount)
себестоимость_строки = знак × quantity × unit_cost(товар, дата продажи)
```

Простыми словами: отмена — операции не было; возврат вычитается из продаж; скидка уменьшает выручку.

## 2. Метрики

### М-01. Выручка
- **Формула:** `Σ чистая_выручка` за период по выбранному срезу.
- **Единица:** рубли.
- **Нулевые значения:** если продаж нет — `0` (это правда: продаж не было). Если чистая выручка отрицательна (возвратов больше, чем продаж в периоде) — показываем значение и отмечаем флагом «возвраты превышают продажи».

### М-02. Валовая прибыль
- **Формула:** `М-01 − Σ себестоимость_строки`.
- **Себестоимость:** версия, действовавшая на дату продажи (as-of соединение: последняя запись `valid_from ≤ дата продажи`).
- **Если себестоимость на дату не найдена или невалидна:** строка исключается из М-02 и М-03, но остаётся в М-01; число исключённых строк выводится рядом с показателем («рассчитано по 98,7% выручки»). Это честнее, чем считать себестоимость нулевой.
- **Не путать:** это не операционная прибыль — аренда, зарплаты, доставка не вычитаются.

### М-03. Валовая маржинальность
- **Формула:** `М-02 / М-01 × 100%` (оба показателя — по одному и тому же набору строк с валидной себестоимостью).
- **Выручка = 0 или < 0:** результат `NULL` («н/д»), не 0% и не ошибка деления.
- **Агрегация:** только как отношение сумм. **Нельзя** усреднять маржинальность товаров — среднее процентов даёт неверный итог.

### М-04. Наценка
- **Формула:** `(цена − себестоимость) / себестоимость × 100%`.
- **Себестоимость ≤ 0 или отсутствует:** `NULL` + предупреждение INVALID_FIN_DATA.
- **Отличие от маржи** (обязательный тест): при цене 200 ₽ и себестоимости 100 ₽ наценка 100%, маржа 50%. Связь: `маржа = наценка / (1 + наценка)`.

### М-05. Средняя цена реализации
- **Формула:** `Σ чистая_выручка / Σ чистое_количество`.
- **Чистое количество ≤ 0:** `NULL`.
- Это цена **после скидок**, она может быть ниже цены прайса — так и должно быть.

### М-06. Доля товарных предложений ниже минимальной маржи
- **Числитель:** активные предложения с валидными данными, у которых плановая маржа `(цена − себестоимость)/цена < min_margin` применимого правила.
- **Знаменатель:** активные предложения с валидными данными (цена > 0, себестоимость > 0, есть правило).
- **Знаменатель = 0:** `NULL`.
- **На дату:** считается на дату «as of», а не за период (это свойство цен, а не продаж).
- Предложения с невалидными данными в знаменатель **не** входят, но показываются отдельным счётчиком «исключено из-за ошибок данных: N».

### М-07. Плановая маржа предложения (вспомогательная)
`(цена − себестоимость) / цена`. При цене ≤ 0 или отсутствии — `NULL`.

## 3. Правила ценообразования

### Параметры правила

| Поле | Тип | Ограничение | Смысл |
|---|---|---|---|
| `target_margin` | доля | `0 ≤ x < 1` | Целевая маржа |
| `min_margin` | доля | `0 ≤ x ≤ target_margin` | Ниже нельзя опускаться |
| `max_change` | доля | `0 < x ≤ 1` | Максимальное изменение цены за один пересмотр (0,10 = ±10%) |
| `rounding_step` | рубли | `> 0` | Шаг цены на витрине (по умолчанию 10 ₽) |
| `rounding_mode` | перечисление | `up`, `nearest`, `down` | Направление округления базовой цены |
| `allow_decrease` | логический | — | Разрешено ли рекомендовать снижение цены (по умолчанию нет) |

Целевая маржа 100% (`1,0`) запрещена ограничением БД и проверкой в коде: формула `C / (1 − 1)` — деление на ноль.

### Область действия и приоритет

Правило задаётся для одного уровня: `product` → `category` → `store` → `global`. Для предложения берётся **самое конкретное** действующее правило (первое найденное в этом порядке). Глобальное правило обязано существовать — иначе расчёт не запускается.

### Версии

Набор правил (`rule_set`) имеет номер версии и дату начала действия. После того как набор использован в расчёте, он **не редактируется** — изменение создаёт новую версию. Так любую старую рекомендацию можно объяснить.

## 4. Алгоритм рекомендуемой цены

Обозначения: `C` — себестоимость единицы, `P0` — текущая цена, `mt` — целевая маржа, `mmin` — минимальная, `Δ` — max_change, `s` — шаг округления.

Функции округления на шаг: `ceil_s(x)` — вверх до кратного `s`, `floor_s(x)` — вниз, `round_s(x)` — к ближайшему (половина — вверх).

```
Шаг 1. Проверка данных
   товар неактивен или точка неактивна        → BLOCKED, INACTIVE
   C отсутствует или C ≤ 0                    → BLOCKED, INVALID_COST        (+ алерт CRIT)
   P0 отсутствует или P0 ≤ 0                  → BLOCKED, NO_CURRENT_PRICE    (+ алерт CRIT)
   правило не найдено / параметры вне границ  → BLOCKED, INVALID_RULE        (+ алерт CRIT)

Шаг 2. Базовая цена
   P_base = C / (1 − mt)

Шаг 3. Округление
   P_r  = round_by_mode(P_base, s, mode)
   P_min = ceil_s( C / (1 − mmin) )          — минимальная допустимая цена на витрине

Шаг 4. Минимальная маржа
   если P_r < P_min: P_r = P_min,  флаг ROUNDED_TO_MIN
   (это не «подбор»: правило задано заранее и одинаково для всех)

Шаг 4а. Снижение цены
   если P_r < P0 и allow_decrease = false     → NO_CHANGE, ABOVE_TARGET_DECREASE_DISABLED

Шаг 5. Допустимое изменение
   L_high = P0 × (1 + Δ),  L_low = P0 × (1 − Δ)
   если P_r > L_high: P_c = floor_s(L_high), флаг LIMITED_UP
   если P_r < L_low : P_c = ceil_s(L_low),  флаг LIMITED_DOWN
   иначе P_c = P_r
   если после ограничения цена сдвинулась «не в ту сторону»
   (LIMITED_UP и P_c ≤ P0, или LIMITED_DOWN и P_c ≥ P0)   → CONFLICT, STEP_WIDER_THAN_LIMIT

Шаг 5а. Повторная проверка минимальной маржи
   если (P_c − C) / P_c < mmin               → CONFLICT, MIN_MARGIN_VS_MAX_CHANGE
   рекомендованная цена = NULL; в деталях сохраняются P_base, P_min, L_high
   → ручное рассмотрение

Шаг 6. Прочие ограничения
   товар участвует в действующей промоакции в этой точке → ON_HOLD, PROMO_ACTIVE

Шаг 7. Итог
   P_c = P0                                   → NO_CHANGE, WITHIN_TARGET
   иначе                                      → PROPOSED, причина:
         COST_INCREASE        — себестоимость выросла с прошлой версии
         MARGIN_BELOW_TARGET  — маржа ниже целевой при прежней себестоимости
         MARGIN_ABOVE_TARGET  — снижение (только при allow_decrease)
         + флаги LIMITED_UP / LIMITED_DOWN / ROUNDED_TO_MIN
```

### Уточнения, принятые при реализации

- Если последняя версия себестоимости отклонена проверкой качества (ноль или минус), актуальная себестоимость считается **неизвестной**: рекомендация `BLOCKED/INVALID_COST`, в колонке себестоимости — пусто, предыдущая валидная себестоимость сохраняется только в деталях (`last_valid_cost`). Иначе экран показывал бы устаревшую маржу как текущую.
- Стартовые правила (v1): сеть — цель 45%, минимум 30%, лимит 10%, шаг 10 ₽; суши — шаг 5 ₽; наборы — цель 40%, минимум 28%; напитки — цель 55%, минимум 40%, лимит 15%, шаг 5 ₽. Для дешёвых позиций шаг 10 ₽ шире лимита 10%, и почти каждая рекомендация становилась конфликтом `STEP_WIDER_THAN_LIMIT` — это обнаружено на демо-данных и исправлено настройкой правил, а не алгоритмом.
- Конфликт `STEP_WIDER_THAN_LIMIT` для отдельных дешёвых позиций остаётся возможным — это честный результат правил, а не ошибка.

### Статусы рекомендации

| Статус | Значение | Кто меняет |
|---|---|---|
| `PROPOSED` | Предложено изменение | Система |
| `NO_CHANGE` | Изменение не требуется | Система |
| `CONFLICT` | Правила несовместимы, нужна ручная оценка | Система |
| `BLOCKED` | Нельзя рассчитать из-за данных/правил | Система |
| `ON_HOLD` | Отложено из-за ограничения (промо) | Система |
| `APPROVED` / `REJECTED` | Решение по `PROPOSED` или `CONFLICT` (с указанием вручную введённой цены) | Руководитель (роль в демо) |
| `SUPERSEDED` | Заменена рекомендацией более позднего запуска | Система |

### Разобранный пример

`C = 152,40 ₽`, `P0 = 249 ₽`, `mt = 0,45`, `mmin = 0,35`, `Δ = 0,10`, `s = 10`, `mode = up`.

1. Данные валидны.
2. `P_base = 152,40 / 0,55 = 277,09 ₽`.
3. `P_r = ceil_10(277,09) = 280 ₽`; `P_min = ceil_10(152,40 / 0,65) = ceil_10(234,46) = 240 ₽`.
4. `280 ≥ 240` — ок.
5. `L_high = 249 × 1,10 = 273,90`; `280 > 273,90` → `P_c = floor_10(273,90) = 270 ₽`, флаг LIMITED_UP.
5а. Маржа при 270: `(270 − 152,40)/270 = 43,6% ≥ 35%` — ок.
6. Промо нет.
7. **PROPOSED, 270 ₽ (+21 ₽, +8,4%)**, причина «Себестоимость выросла; изменение ограничено лимитом 10%; целевая маржа 45% будет достигнута при следующем пересмотре».

Пример конфликта: при `P0 = 199 ₽` → `L_high = 218,90`, `P_c = 210`, маржа `(210 − 152,40)/210 = 27,4% < 35%` → **CONFLICT**, цена не предлагается.

## 5. Предупреждения (алерты)

| Код | Уровень | Условие (параметры по умолчанию в `settings`) |
|---|---|---|
| `PRICE_BELOW_COST` | CRIT | `P0 < C` |
| `MARGIN_BELOW_MIN` | CRIT | `C < P0` и плановая маржа `< mmin` |
| `INVALID_FIN_DATA` | CRIT | Себестоимость ≤ 0 / нет; цена ≤ 0; ошибка в исходной строке, отклонённая проверкой качества |
| `PRICE_UNDETERMINED` | CRIT | Рекомендация `BLOCKED` из-за отсутствия цены или правила |
| `PRICE_DEVIATION` | WARN | Цена в точке отличается от медианы по сети для товара более чем на 15% |
| `COST_JUMP` | WARN | Новая версия себестоимости отличается от предыдущей более чем на 10% |
| `MARGIN_DROP` | WARN | Фактическая маржинальность предложения за 14 дней ниже предыдущих 14 дней более чем на 5 п. п. (при выручке за каждое окно ≥ 1000 ₽, иначе не проверяем) |
| `RULE_CONFLICT` | WARN | Рекомендация `CONFLICT` |
| `RUN_COMPLETED`, `PRICE_CALCULATED`, `NO_CHANGE_NEEDED`, `RECOMMENDATION_APPROVED` | INFO | Пишутся **в журнал событий**, а не по одному алерту на каждое из 2 250 предложений — иначе список предупреждений станет бесполезным. `RECOMMENDATION_APPROVED` — по одному на решение |

### Защита от дублей

- Каждый алерт имеет `dedup_key = sha256(код | store_id | product_id | версия_правил | контекст)`, где контекст — например, `valid_from` версии себестоимости для `COST_JUMP`. Версия правил входит в ключ только для алертов, которые от правил зависят (`MARGIN_BELOW_MIN`, `RULE_CONFLICT`, `PRICE_UNDETERMINED`): новая версия правил не должна «воскрешать» предупреждения о данных.
- Частичный уникальный индекс: `UNIQUE (dedup_key) WHERE status IN ('NEW','IN_PROGRESS')`.
- Повторное обнаружение того же открытого алерта → `INSERT … ON CONFLICT DO UPDATE SET last_seen_at, occurrences = occurrences + 1`. Новой строки нет.
- Если алерт был закрыт (`RESOLVED`), а проблема повторилась — создаётся новый: это новое событие.

### Защита от повторного запуска расчёта

`idempotency_key = sha256(as_of_date | rule_set_version | отпечаток данных)`, где отпечаток — хэш от максимальных `loaded_at` и количества строк цен, себестоимости и промо.
- Тот же ключ и запуск уже завершён → новый расчёт не создаётся, пользователь видит существующий запуск.
- Явный «Пересчитать принудительно» → новый запуск, старые рекомендации со статусом `PROPOSED` получают `SUPERSEDED`.

## 6. Сценарный анализ

Базовое количество `q0` — чистые продажи предложения за последние 28 дней до даты расчёта.

Пользователь выбирает режим:
1. **Фиксированный спрос** (по умолчанию): `q1 = q0`.
2. **Коэффициент реакции спроса** `e` (задаётся вручную, по умолчанию −0,5): `q1 = max(0, q0 × (1 + e × Δp))`, где `Δp` — относительное изменение цены. При `e = −0,5` рост цены на 10% снижает продажи на 5%.

Показываем до/после: выручка `P × q`, валовая прибыль `(P − C) × q`, маржинальность, изменение цены в % — по точкам, категориям и итогом.

**На экране и в экспорте всегда выводится блок «Допущения»:** режим, значение `e`, базовый период, что себестоимость считается неизменной, что промо и скидки не моделируются, и фраза «Это сценарий, а не прогноз фактического результата».

В сценарий попадают только `PROPOSED`. `CONFLICT`, `BLOCKED`, `ON_HOLD` остаются по текущей цене и считаются отдельной строкой.
